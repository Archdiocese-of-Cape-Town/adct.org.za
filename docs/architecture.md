# Architecture

The parish intake system is a single WordPress plugin (`adct-parish-intake`) running on the existing adct.org.za site on xneelo shared hosting. It collects parish communications, extracts events from them, checks them with the submitter, and publishes them to a public events page with an ICS feed.

## Goals

- Mostly **non-technical operators**: no extra servers, no daemons, no command line needed day to day.
- **Runs within shared-hosting limits** (see [hosting environment](hosting-environment.md)).
- **Offline first**: deterministic parsing by default; AI and OCR are optional plug-ins that always fall back.
- **Human in the loop at low cost**: the submitter confirms their own events by email, then a dean or an archdiocese reviewer approves them, straight from an email if they like.
- **Testable**: the domain core runs without WordPress.

## Components

### 1. Domain core (`src/Core/…`, no WordPress dependency)
Pure PHP 8.2, covered by unit tests and loaded through Composer PSR-4:
- `Parsing` – the stage pipeline (normalise → split into blocks → rule extraction → directory lookup → date/time → recurrence → event-type keyword classification → confidence → optional AI). The WordPress adapter loads editable term-meta keyword lists each time a pipeline is created; Core receives only term slugs and phrases. Classification stores `event_type`, separate `event_type_confidence` and `event_type_source` in candidate fields. A unique highest score selects a type; ties and no match select Other with low type confidence. The publishing adapter assigns the type on new events and leaves an existing type intact on automatically classified updates.
- `Recurrence` – RRULE model and expansion of upcoming occurrences (Africa/Johannesburg).
- `Matching` – duplicate/update detection between candidates and existing events.
- `Trust` – decides the next step for a candidate: send for confirmation, route to the approval queues, publish (self-approval or a verified contact's change to a published event), or ignore.
- `Approval` – parallel dean/reviewer queues, atomic "first to act wins", self-approval, reminders.
- `Directory` – parish/contact import and parser-facing parish and venue lookup over active names, aliases and suburb-qualified names, returning parish/venue IDs and venue coordinates.
- `Sources` – typed source registry and `SourceHealthRecorder`; the WordPress source repository persists registry and health state without putting WordPress dependencies in the core.
- `Ingestion` – `MailboxPollingJob` polls active email sources by UIDVALIDITY and UID, within the job runner's time/item budgets. It stores each raw RFC 822 message and eligible attachments before advancing the mailbox checkpoint, de-duplicates by source plus Message-ID or a versioned content hash, and moves completed mail to Processed. Oversized messages are recorded as skipped and moved to Too large; attachment policy failures remain visible in admin. The polling stage detects declared and likely automated/list mail, stores a conservative `is_auto_reply` no-confirmation flag, and parses SPF/DKIM/DMARC `Authentication-Results` claims into versioned structured data. Authentication claims are untrusted unless the authserv-id matches an explicitly configured receiving-MTA ID; the default allowlist is empty. The separate `InboundMessageProcessingJob` reads the same protected `.eml` file, fills `body_text`, and transactionally refreshes draft candidates without publishing events or sending mail. Blocked senders are ignored; automated/list messages with candidates remain drafts for review and those without candidates are ignored. Failures are stored as operator-facing reasons and log only the message ID, processing context and exception class; Inbox reprocessing requeues only failed records and preserves their identity, raw file, attachments and mailbox checkpoint. `MimeMessageParser` decodes raw RFC 822 mail into `Message` + attachment metadata using the pure-PHP `zbateson/mail-mime-parser` dependency; it decodes multipart/alternative, related and mixed bodies, transfer encodings and charsets, selects useful plain text before HTML, and retains thread/list/automation/authentication headers without interpreting authentication results.
- `Ingestion\Imap` – `ImapMailbox` currently implements `MailboxInterface` with a bounded pure-PHP IMAP client. It searches by UID, fetches raw RFC 822 bytes and metadata, lists/creates folders, marks messages seen, and moves them using MOVE or COPY/STORE/EXPUNGE. Successful moves return an ownership receipt only when the server supplies a valid, exact `COPYUID` mapping. It checks message size before fetching the body (30 MiB by default) and uses PHP stream sockets with TLS peer verification enabled by default; unencrypted or unverified connections require an explicit test-only opt-in. ADR 0017 supersedes the client choice in ADR 0013; a library-backed replacement has not yet landed.
- Mailbox settings use a validated Core value object and a connection-test service. The service logs in, counts unseen messages in the inbox, checks the processed folder, closes the connection, and records only safe success/failure health details; it does not fetch message bodies or poll.
- The poller stores raw `.eml` files and accepted attachments in an unguessable-name `private` uploads subdirectory with deny rules and an `index.php` guard. Attachments are stored only when both their declared MIME type and file signature are allowed; the provisional allowlist is PDF, JPEG, PNG, WebP, HEIC and HEIF, with a 15 MiB per-file cap. Skipped attachment metadata and oversized-message errors are shown on the Mailboxes screen.
- Processed-folder retention records only exact server-issued move receipts, scoped to the source, mailbox identity and destination UIDVALIDITY. Cleanup deletes only those exact recorded UIDs when the mailbox still matches; existing or untracked mail is never selected, and stale ownership records are discarded without touching the mailbox.
- `Support\EmailTextCleaner` – reusable plain-text cleanup that separates quoted replies and signatures, extracts original forward headers, and removes common newsletter footers. `Support\HtmlToTextConverter` preserves paragraphs, lists and table rows without requiring `ext-dom`.
- `Tokens` – random, SHA-256-hashed, single-use action tokens and renewal-link rate limits.
- `Jobs` – due checks, bounded item processing, checkpoints, lock/state ports and run results.

The core talks to the outside through interfaces (ports): `MailboxInterface`, `ClockInterface`, `EventRepositoryInterface`, `DirectorySnapshotProviderInterface`, `AiProviderInterface`, `OcrProviderInterface`, `MailerInterface`, `MailDeliveryInterface`, `MailQueueRepositoryInterface`, `RecipientPolicyInterface`, `InboundMailStorageReaderInterface`, `InboundMessageProcessingStoreInterface`, `EventCandidateStoreInterface`, the action-token store/rate-limit/key/renewal/handler ports, and `HttpClientInterface`. The parsing pipeline, its stages and value objects live under `Core\Parsing`; shared pure-PHP helpers live under `Core\Support`; contracts live under `Core\Ports`. `MailerInterface` accepts one validated recipient and queues a fully composed HTML/text message with a priority and optional idempotency key. The Core queue service also exposes pending-count/oldest-age statistics. Future confirmation and approval flows inject this port; inbound processing does not depend on it. Action-token renewal is queued through this port at login/confirmation priority; action-specific confirmation, login and approval handlers remain separate behind the typed handler registry. The WordPress wiring reads operator-managed Test mode settings dynamically and applies the recipient policy both when mail is queued and immediately before a queued row is claimed for delivery. Test mode is off by default, supports exact addresses and exact domains, and persists blocked rows as `suppressed`; empty or invalid settings fail closed. This policy applies only to the Parish Intake queue, not to unrelated WordPress mail.

`Message` keeps the received sender/date and envelope subject, plus separate quoted text, signature text, original-forward metadata, and raw values for Message-ID, In-Reply-To, References, Auto-Submitted, List-Id and Authentication-Results. Attachment records identify the corresponding MIME part and Content-ID. Stored PDF attachments are read for their text layer during processing: `PdfTextEnrichmentService` resolves each stored name to a real path through the storage port, extracts the text, records `extracted_text`, `extraction_method` and a status on the attachment row, and appends the text to the message body as a marked section before parsing, so the rest of the pipeline is unchanged. Extraction is never fatal — a missing, oversized, page-capped, slow or unreadable PDF is recorded and listed for manual entry on the Manual parser screen, and the email is still processed ([ADR 0015](decisions/0015-pure-php-pdf-text-extraction.md)). The MIME and PDF parser dependencies are namespace-prefixed into release packages with Strauss (ADR 0012).

Stored image attachments are read for their text during processing when optional OCR is switched on. `OcrTextEnrichmentService` takes the message's unreadable images from `AttachmentRepository`, asks `OcrProviderInterface` for their text, records `extracted_text`, `extraction_method` and a status on the attachment row, and appends the text to the message body as a marked section before parsing, exactly as `PdfTextEnrichmentService` does, so the rest of the pipeline is unchanged. Like the PDF path, extraction is never fatal: a declined opt-in, a missing key, a provider timeout, a rate limit, an unreadable type, an oversized image or a provider error all leave the message untouched, are recorded on the attachment row and are listed for manual entry on the Manual parser screen. The first adapter is `OcrSpaceProvider`, which posts the image to OCR.space; it never throws, and it holds the API key in a private closure so the key cannot be reached by dumping the object. OCR is off by default, has its own `OcrSettings` daily call limit counted independently of the AI fallback, and runs only inside the queue behind a hard per-message time budget — never during an admin page load ([ADR 0021](decisions/0021-opt-in-server-side-queue-ocr.md)). Values that came out of a photograph are marked, not trusted: `Pipeline` records which block the marked OCR section opens, and `ConfidenceScoringStage` adds the `ocr` weakness flag to every field of a candidate parsed from that block onwards, which charges `CandidateScorer`'s `ocr` penalty on top of whatever origin it already earned. A plainly printed date on a poster is genuinely `explicit`, so the origin is kept and only the flag is added — that records *how the characters were read* rather than flattening every poster value to indistinguishably machine-read. At the calibrated penalty a poster `explicit` date lands below both the field and review thresholds, so it is flagged uncertain in the submitter's preview and held for a human, while an imperfect poster still yields a usable candidate rather than a blank one. Because a flag is only ever charged when something sets it, no candidate parsed without OCR changes score. Client-side OCR (ADR 0018) remains the complementary path for a reviewer who is present, and is unaffected.

The IMAP protocol uses `Ingestion\Imap\TransportInterface`; `StreamTransport` lives in `src/Core` because it uses only PHP's standard stream API and no WordPress functions. The adapter never logs LOGIN commands or credentials. A message over the configured fetch limit raises `MessageTooLarge` after a size-only FETCH, before its body is requested.

`Pipeline::parseAll(Message)` returns a `ParseOutcome` containing ordered event candidates, shared notes/errors and block metadata. Before shared-context extraction or event-candidate classification, the deterministic `SectionSkipper` filters recognizable non-event sections: Mass times and intentions, sick lists, deceased, anniversaries, raffle winners, collections/finances, banking details and readings. Its case- and punctuation-insensitive phrase lists have Core defaults and can be edited from Parish Intake → Settings. Weekly Mass-times tables are also recognized from weekday/time rows that identify Mass or Service. A standalone category phrase or a category match formatted as a Markdown/underlined, all-caps, colon-terminated or otherwise recognized heading starts a section skip through the next heading, even when that section contains dates and times. A category phrase at the start of running text is skipped only when its block has no explicit date plus time or event noun; a block with that event signal is retained as a candidate, receives the text-free `section_keyword_overridden: <category>` note and has its confidence reduced by 0.1. For skipped sections, the outcome retains only the zero-based `block_index`, `classification: skipped` and category `reason`, plus a count-by-category note. Skipped text is not used in candidates, shared context, descriptions, notes, block metadata or AI input.

The `BulletinBlockSplitter` then uses headings, blank-line groups, list items, date-led lines and pipe-delimited table rows; it passes safe parish, month/year, venue and masthead context to each candidate without using AI. A masthead near the top of the bulletin is blanked before block detection and held as context, because a two-line "Parish Newsletter / September 2026" header otherwise reads as an event of its own and outranks the block holding the real event. Masthead recognition is shared with `RuleBasedExtractionStage` through `Core\Parsing\BulletinMastheadMatcher`, so the two stages cannot disagree about which forms exist ([#133](https://github.com/Archdiocese-of-Cape-Town/adct.org.za/issues/133)). That stage reads one time range per candidate, from either the "from X to Y" form or a dash-joined pair, and resolves each end against the other so that a single meridiem governs both ends; a dash-joined pair of bare numbers is only a time range when one end carries a meridiem, and every end is matched against the same scripture-citation spans so a verse range is never read as a time ([#153](https://github.com/Archdiocese-of-Cape-Town/adct.org.za/issues/153)). Each candidate has a zero-based `block_index` and a trimmed `source_snippet` capped at 2,000 characters. To bound work and review output, the provisional `ParseOutcome::MAX_CANDIDATES` limit is 50: an over-limit message returns the first 50 in document order, reports `candidate_limit_exceeded:<total>`, and lowers retained candidates' confidence to zero with reprocessing flagged for manual review. Other obvious non-event blocks are reported as notices/skipped blocks rather than event candidates.

The `DirectoryLookupStage` runs after deterministic extraction and before confidence scoring. Its `DirectoryLookup` uses the pure-PHP `DirectorySnapshotProviderInterface`; the WordPress adapter supplies active venue records, parish names/area/church/suburb data and sender trust links from a versioned transient snapshot. A single verified parish link supplies the parish and its default venue. A verified sender linked to several parishes is disambiguated only by a unique text/context match; pending and unknown senders use text/context only, and blocked senders are left unchanged for intake to ignore elsewhere. Parish matching reuses `VenueNameNormalizer` for St/Saint, punctuation and apostrophe variants and also checks suburb-qualified names. An unqualified church-name-only body-text match without verified-sender support has 0.6 confidence; fuller or suburb-qualified matches and explicit block context retain their existing confidence. Matched IDs, venue coordinates, source and confidence are added as new `fields` and text-free notes; a labelled venue is retained unless it matches a directory venue. Parish, venue or contact writes advance the directory version so the next lookup lazily rebuilds the cached snapshot.

The existing `Pipeline::parse(Message): ParseResult` API remains compatible and returns the first candidate (or a notice result when none were found); optional AI enrichment remains a later, separate pipeline stage.

### Confidence scoring

This is a reliability check for deciding what a person needs to check, not a ranking of events or a statistical probability of correctness. "Penalty" below means lowering the reliability indicator when the parser guessed or found conflicting information; it never means penalising a parish or submitter.

Use the default overall review threshold of 0.55 and field warning threshold of 0.60. Operators do not need to tune them to use the plugin. Keep review routing independent of optional AI enrichment: enabling AI must not change the human-review rules. A weak title or date already holds the candidate for review even if its overall score is acceptable. Do not add a permanent publication ban based on parser evidence; a person can check and correct the notice through the existing confirmation and approval workflow. Every new event still requires dean or Archdiocese approval.

Unsupported values in both HTML and plain-text confirmation previews are explicitly labelled as guesses not stated in the notice, distinct from ordinary uncertain values. Keep the extraction defects tracked in #128 and #129 separate: this change makes unreliable extraction visible, not correct. The numerical defaults and weights are adjustable implementation details under the existing offline-first and human-approval decisions, not a new ranking policy requiring a separate ADR.

`ConfidenceScoringStage` is a thin stage that delegates to the pure-PHP `CandidateScorer`. Every stage that sets a field records a `FieldEvidence` value object at the same moment — the origin (was this read from the notice, taken from the directory, inferred, filled by AI, or *not supported at all*?) plus any specific weakness flags. Scoring itself happens once, at the end, from that evidence, so a value's score cannot drift from how it was obtained.

This exists because a plausible-looking value the parser invented was previously indistinguishable from one it actually read ([#43](https://github.com/Archdiocese-of-Cape-Town/adct.org.za/issues/43), [#130](https://github.com/Archdiocese-of-Cape-Town/adct.org.za/issues/130)). A field marked `unsupported` now scores 0 *and* reduces the overall score, rather than counting as if it were extracted.

The field score is a base value per origin, less a penalty per weakness flag, clamped to 0–1; the flags include the `ocr` penalty charged on values read out of an image attachment (see the OCR paragraph above). The overall score is the weighted mean of the field scores, scaled by how much of the candidate's field weight actually carries a value, less a charge for every `unsupported` field and for a missing required field, and less any whole-candidate penalty such as a stated weekday that contradicts the parsed date. Weights are `title` 3, `event_date` 3, `event_time` 2, `parish_name` 2, then 1 each for `venue`, `event_type`, `contact`, `description` and `recurrence`; `title` and `event_date` are required. A missing required field is charged directly rather than only lowering coverage, because the weighted mean already divides by present weight and would otherwise absorb the penalty entirely.

The result is stored in the candidate's scalar `confidence` column and, per field, in the `field_confidence` JSON key described in the [data model](data-model.md). Two admin settings move the routing points: `adct_parish_intake_confidence_threshold` (default 0.55) is the overall score below which a candidate is routed to human review, and `adct_parish_intake_field_confidence_threshold` (default 0.60) is the per-field score below which a value is marked as uncertain in the submitter's preview email. Both are editable under Parish Intake → Settings; the review threshold is deliberately separate from the AI-enrichment threshold so that turning AI on or off does not change where candidates are routed. A low overall score does not mark well-evidenced fields as doubtful — that would ask the submitter to re-check the best-supported part of their notice — and a field with no recorded score is not treated as weak, because absence of evidence about a field is not evidence that the field is doubtful.

`RecurrenceDetectionStage` converts recognized deterministic phrases into a supported RFC 5545 RRULE, keeps the source phrase as human-readable text, and validates every emitted rule with `RRuleValidator` (using `RRulePresetMapper` for the matching presets). When a recurring candidate has no explicit `event_date`, its anchor is the first matching occurrence on or after the date parser's reference date: a bulletin date range when present, otherwise the received date or injected clock. This adds the `recurrence_anchor_inferred` note and reduces confidence by 0.05. A yearless recurrence end date is resolved to its next calendar occurrence on or after the anchor and noted. Seasonal wording such as "daily during Lent/Advent" remains ambiguous: no liturgical date, anchor or RRULE is guessed; the candidate is flagged for confirmation with `recurrence_ambiguous_season` and the ambiguity confidence penalty.

The WordPress-free `OccurrenceExpander` expands the validated DAILY, WEEKLY, MONTHLY and YEARLY subset in `Africa/Johannesburg` local time. The inclusive rolling window runs from the current site-local date through the same date one year later, clamping a leap-day anniversary to February 28. RRULE UNTIL is inclusive; DTSTART is retained as the first instance and counts once even if it does not match the filters; COUNT applies to RRULE instances before exclusions, RDATEs do not consume COUNT and may fall after UNTIL, and EXDATE removes a matching RRULE or RDATE start. Positive BYDAY ordinals count from the start of the month/year, while negative ordinals count from the end (for example, `-1SU` is the last Sunday and `-1FR` the last Friday). Missing fifth weekdays do not spill into another month, and a February 29 yearly rule has no generated instance in non-leap years. These semantics are provisional and reversible. The daily `expand_occurrences` job checkpoints its event cursor and fixed window, so a budget-limited batch resumes without shifting the window.

The Manual parser displays the full `ParseOutcome` and uses the same cached directory lookup as the parser pipeline, so admins can enter a sender email to test verified-sender resolution. It is diagnostic-only: it writes to the legacy prototype table using the first candidate (or the notice result when there are no candidates), but does not create inbound-message/candidate rows or enqueue confirmation email. Only the background inbox-processing and confirmation jobs handle stored inbound mail.

### 2. WordPress adapters (`src/WordPress/…`)
- Plugin bootstrap and hook wiring, the manual parser/admin UI, database schema/repository access, static reports, and the WordPress HTTP client.
- `WordPress\Ai\OpenAiCompatibleProvider` implements the core AI port and receives `HttpClientInterface`; only `WordPress\Http\WordPressHttpClient` calls `wp_remote_post`. An atomic daily reservation uses the existing hashed rate-limit table; HTTP 429 and 5xx set a cooldown. Cron-driven inbox processing alone enables AI: the Manual parser and admin-triggered synchronous reprocessing use deterministic parsing.
- Repositories using `$wpdb` (custom tables in the site's existing WordPress MySQL database) and the `adct_event` post type.
- `WordPressDirectorySnapshotLoader` reads parish, venue and contact repositories; `WordPressDirectorySnapshotCache` stores the snapshot in a transient keyed by the non-autoloaded directory version option. Parish, venue and contact repositories increment that version after successful writes.
- Admin screens (dashboard, review/approval queue, parishes, deaneries and approvers, sources, mailboxes, Inbox, settings, outbound email, health). Mailboxes are linked to archdiocese-wide email sources; the Mailboxes screen supports settings, an explicit test-connection action and skipped-message/attachment notices. The review-capability Inbox lists message status and safe error notes and offers single or bounded bulk reprocessing of failed messages. It does not display raw message content or attachments. The Outbound email screen manages queue-only Test mode and shows escaped previews of recent suppressed rows to settings managers. Parish sources are editable from each parish's Sources tab; the Sources submenu also lists all sources and manages archdiocese-wide ones.
- On-demand client-side OCR for image posters ([ADR 0018](decisions/0018-client-side-ocr-for-image-posters.md)). Two read-only endpoints serve a stored image from the protected uploads directory to a browser that is already allowed to see it: `AttachmentImageEndpoint` (`admin-post.php`, review capability, id validation, and a nonce bound to that attachment id) on the Manual parser screen, and `ActionTokenImageEndpoint` on the emailed action-token page, where `CandidateSourceImageResolver` resolves the token's own candidate to the message image and nothing else, so a link cannot enumerate other candidates' posters. `AttachmentImageEndpoint` also serves the #63 candidate detail screen, which previews the candidate message's first stored browser-readable image beside the edit form. Neither endpoint relaxes the deny rules on the `private` directory, exposes a storage name, or consumes the token it serves. `OcrControl` renders the same button markup and the same settings panel on both surfaces, and `assets/ocr.js` runs tesseract.js (pinned version, loaded from jsDelivr only when the button is clicked) to fill the description field in the browser. The tunables live in `assets/ocr-settings.js`, a DOM-free module holding the layout list, the page-segmentation mode each layout maps to, the confidence cut and the panel wiring, so the decisions that matter can be tested in Node without a browser, a worker or the 12 MB language download; it is loaded before `ocr.js` so the module can read its layout list at start-up. `OcrControl` renders that panel inside a native `<details>` labelled **Advanced**, so a reviewer sees a button and a poster rather than a form; the disclosure works before the deferred scripts run and with JavaScript off, and the browser wires the summary to it. The Tesseract PSM behind each choice rides in `title` attributes on the disclosure and on every option, so the number is one hover away without being something an ordinary reviewer has to read. A layout choice re-reads the image; a confidence change re-filters the reading already in the browser. Neither is stored or sent, and the defaults reproduce the behaviour the control had before the settings existed. Extracted text is never sent back to the server, so no row, column or schema version changes; the reviewer's confirmation remains the source of truth, and manual entry stays available when OCR is skipped or fails.
- Front-end approver queue for deans, shipped in #72. `[adct_approval_queue]` (block `adct/approval-queue`) renders the same scoped candidates, decisions and changes as the admin screen on a public page, and `[adct_approval_queue_login]` (`adct/approval-queue-login`) renders the sign-in form for anyone not signed in. `MagicLinkLoginRequestPage` renders the form and posts to `admin_post_adct_pi_request_magic_link`; `MagicLinkLoginService` resolves the address, rate-limits it through the existing action-token limiter and enqueues the link through `WordPressMagicLinkDelivery`, so no mail bypasses the queue. `LoginHandler` consumes the previously reserved `ActionTokenPurpose::LOGIN` at its 30-minute lifetime: `preview()` shows a confirmation page and only `perform()` signs anybody in, so the token is single-use and a link scanner cannot open a session. The gate is the same dual capability check the admin queue uses, and `FrontEndApprovalQueue` re-resolves the live deanery scope on every action rather than trusting the page: `ReviewQueueRepository::findScoped()`, `decide()` and the new `recentChanges()`/`findScopedChange()` all scope in SQL against the caller's own active assignments, so an item posted from another deanery resolves to null or raises `This candidate is outside your review queue.` `changeScope()` is deliberately not `where()`: a change carries no parish of its own, so it inherits the candidate's parish and falls back to the event's `parish_id` post meta, which is what keeps changes to already-published events visible to the dean who owns them. Revert stays an emailed single-use link ([ADR 0008](decisions/0008-deans-never-need-wp-admin.md)); the front end only requests one.
- Public views: the server-rendered `[adct_events]` shortcode and `adct/events` block read bounded pages from the indexed occurrences table, join only published posts, and render day-grouped cards with local dates. Preset week/month and validated custom ranges share ordinary GET links, so JavaScript is not required. Short-lived transients use fixed keys for at most three presets and 100 pages; their stored generation and time window must match before reuse. Arbitrary date ranges bypass transient writes to avoid unbounded options growth. An event write, status change, term assignment or occurrence replacement rotates the generation, and cached rows are rechecked against the published post status before display. The public `?adct_ics=1` calendar endpoint selects up to 500 distinct published events with occurrences in the rolling year; optional `parish` (ID) and `type` (term slug) filters avoid unbounded transient keys, while the all-events feed uses one fixed 60-second cache key. Single event pages use a theme-overridable fallback template, show only published event data, and expose a single-event ICS download plus Google Calendar link. The feed renders through the WordPress-free `Core\Events\IcsCalendar`: event times are emitted as `DTSTART;TZID=Africa/Johannesburg` alongside an explicit `VTIMEZONE` (never a floating or naive local time, so the feed is safe for calendar clients in other zones), all-day starts use `VALUE=DATE` with an exclusive end, `UID` is derived deterministically per event, `DTSTAMP` comes from the injected clock, and every text value is stripped of control characters, repaired if the input is not valid UTF-8, escaped and folded to 75 octets with CRLF line endings. Summaries and descriptions are truncated so a feed reader cannot be handed a megabyte of bulletin text.
- Scheduled jobs via WP-Cron hooks, triggered by site traffic, a 2-hourly xneelo cron backstop, an optional external pinger and a "Check now" button ([ADR 0010](decisions/0010-scheduled-jobs-with-2-hour-cron-limit.md)).
- Queued mailer (`adct_pi_mail_queue` → the site's `wp_mail`/FluentSMTP route) with per-recipient messages, an hourly cap, priorities, retries and sanitized queue statistics ([ADR 0011](decisions/0011-outbound-email-queue-with-hourly-cap.md)), `wp_remote_*` HTTP client, roles and capabilities.

The Composer PSR-4 mappings keep `ADCT\ParishIntake\Core\…` and `ADCT\ParishIntake\WordPress\…` separate. The release zip includes a small source autoloader in `WordPress\Autoloader` alongside the namespace-prefixed Composer dependency loader; development and tests use Composer's generated autoloader.

### 3. Infrastructure adapters
- `ImapMailbox` – the Core's PHP-stream IMAP client (no `ext-imap` or additional Composer package); retrieval and folder operations are behind `MailboxInterface`. GreenMail integration tests verify protocol operations, polling resume and de-duplication, oversized-message handling, and the connection-test service's success, wrong-password and missing-processed-folder results.
- `IcsSource` – fetches and parses ICS feeds (Google Calendar).
- `PrinsFrankPdfTextExtractor` – pure-PHP text extraction through `prinsfrank/pdfparser` that uses text positions to rebuild columns, because most bulletins have 2–3 columns ([parser findings](parser-samples.md)). Gated by size, page and time limits before and during extraction ([ADR 0015](decisions/0015-pure-php-pdf-text-extraction.md)).
- Optional `OcrProvider`s (OCR.space free tier, OpenAI-compatible vision models) – off by default.
- Optional `OpenAiCompatibleProvider` for AI enrichment (OpenRouter `:free` models, Groq, local Ollama during development).

## Scheduled jobs

The framework in `src/Core/Jobs` is WordPress-free. A job decides whether it is due and processes one item per step. `JobRunner` acquires a lease, loads the last checkpoint, processes items until the **60-second time budget** or **100-item budget** is reached, saves each returned checkpoint, and releases its token in `finally`. The budgets are configurable through the runner constructor or per-run arguments. The default lock lease is 180 seconds, longer than the time budget. Jobs receive time through `ClockInterface`.

Each job's state records `last_run_at` (run start), `last_success_at` (updated only after a non-failing batch), the last error message and timestamp, the last run's item count, and its checkpoint. A budget-limited batch is a successful run: its checkpoint is saved and the next due run resumes there. A failed batch records the error without moving `last_success_at`.

`WordPressJobStateStore` stores state in non-autoloaded WordPress options; no database migration or custom table is needed. `WordPressJobLock` uses `add_option` for atomic creation. Expired or malformed locks are removed with a prepared compare-and-delete against the exact stored value, and release also checks the holder's random token so an old holder cannot remove a replacement lock. The WordPress scheduler registers one custom ten-minute WP-Cron event per job; each job's due check prevents unnecessary work between its own intervals. Scheduling and cleanup failures are logged without aborting visitor requests or plugin deactivation. An unexpected cron callback failure is logged and recorded in job state when the state store is available.

| Job | Default interval | Work |
|---|---|---|
| `framework_heartbeat` | due every 10 min | Currently registered framework check only; no parish data or email work. |
| `poll_mailboxes` | due every 10 min | Check active mailboxes whose source interval has elapsed, resume incomplete UID scans, and retry failures with backoff; store raw mail and eligible attachments, de-duplicate and file completed messages. Parsing is a later job. |
| `queue_confirmation_previews` | due every 10 min | Select the oldest parsed inbound message with draft candidates and no confirmation outcome; first recover any row for its fixed confirmation group key and verify recipient/payload so retries preserve the queue's status before current sender-policy suppressions, then compose and enqueue a new eligible preview with bound action tokens and validated thread headers. |
| `process_inbound_messages` | due every 10 min | Parse received/interrupted messages from their existing private files, update status/error and idempotently refresh draft candidates. Inbox retries prioritize up to 20 failed records through this bounded job. |
| `queue_approval_notices` | due every 10 min | Queue at most one grouped, 20-event notice per eligible approver per run, or one daily digest per recipient. Digest recipients are skipped until the site's digest hour (`ADCT_PI_APPROVAL_DIGEST_HOUR`, default `07:00` `Africa/Johannesburg`), so "daily" means one digest a day even when cron runs soon after an arrival. Persist each candidate/recipient assignment before enqueueing so a retry cannot mint another email; deferred items remain eligible on the next run. |
| `send_mail` | every trigger; scheduled every 10 min | Send queued email in priority order within the job's 60-second / 100-item budget and the rolling hourly cap. A priority-1 enqueue can request one immediate item through the same job lock and cap. |
| `poll_sources` | hourly | Planned: poll a few active ICS/PDF/secondary sources per run (oldest `last_checked_at` first) and record checks, successes, failures and item times through `SourceHealthRecorder`. No source polling adapter is registered yet. |
| `expand_occurrences` | daily | Rebuild published events' occurrences for the inclusive 12-month window; per-event replacement is transactional, and batches resume from a checkpoint. |
| `monitoring` | daily | Email approvers once per event after a configurable idle period (default 3 days) with no decision, and record each send as an `approval_reminder` follow-up. The global switch, the period and each approver's own switch all live outside the job, which reads them on every run. |
| `retention_cleanup` | daily | Delete opted-in raw messages/attachments past their per-message floor, exact receipt-owned Processed-folder messages, expired tokens and old logs in bounded batches. |

The framework heartbeat, `poll_mailboxes`, `process_inbound_messages`, `queue_confirmation_previews`, `queue_approval_notices`, `monitoring`, `send_mail`, `expand_occurrences` and `retention_cleanup` are registered jobs. The heartbeat only exercises scheduling; the mailbox poller stores incoming mail but does not parse messages or process events. `process_inbound_messages` parses existing private message files and creates or refreshes draft candidates; it does not publish events or queue mail. The receipt-scoped `retention_cleanup` job is the only scheduled mailbox-deletion path.

The `monitoring` job is the approval reminder. It scans `awaiting_approval` candidates whose `updated_at` is older than the configured period, re-checks each row's status and `decided_at` immediately before mailing, and sends at most one reminder per event per approver. "At most once" is enforced by the mail queue's unique `(recipient, group_key)` index rather than a new table or column, so a second run stays quiet without a schema change. The reminder reuses the same `APPROVE_EVENT`, `REJECT_EVENT` and `EDIT` action tokens as the approval notice, so a token minted for a reminder is no more authoritative than any other emailed token: each handler re-resolves the live approver relationship, uncached, on both the GET preview and the POST, so a dean who has since moved deaneries cannot act on a reminder minted for them. An item still awaiting a manual match decision is skipped, as it is for the notice. The job holds no reminder logic of its own beyond the scan: the period and the global switch come from an option adapter resolved lazily on each run, and each approver's own switch comes from `ApprovalRecipients`, so no constructor reads a WordPress option.

The confirmation job handles one inbound message per step, considers all of its draft candidates together, and records a safe outcome/reason. Permanently unavailable or invalid raw headers are recorded as terminal failures so an old unreadable message does not block later work; transient storage, database or marker-write failures remain retryable. Before issuing tokens or queueing, it checks the fixed inbound-message group key across recipients: a changed recipient, changed payload or multiple matching rows is an explicit conflict, never a second silently routed confirmation. Matching queue rows are reused. Queue-level test-mode suppression and terminal delivery failures are recorded and are not automatically requeued. Queue delivery continues through the only plugin `wp_mail()` adapter and the site's FluentSMTP setup; neither inbound parsing nor the confirmation job sends directly from a web request.

Priority 1 is login/confirmation, priority 2 approver/change notices, and priority 3 reminders/digests. The default cap is 100 successfully sent recipients in the preceding 60 minutes, configurable from `wp-config.php` through `ADCT_PI_MAIL_HOURLY_CAP` (1–500). Database-atomic claims reserve capacity for in-flight deliveries. A thrown delivery exception or worker interruption with unknown outcome leaves the row in `sending` and holds its reservation for the full 60-minute window before retrying with backoff; a mail accepted by SMTP just before the worker died can therefore be duplicated on that retry. Messages with the same recipient and `group_key` are de-duplicated only after composition: identical payloads return the existing row, and changed content under the same key is an error rather than silently discarded. The key is per recipient and does not coalesce content.

The `expand_occurrences` job reads only published `adct_event` posts. Saves from the manual editor and REST API rebuild one event immediately; moving an event away from Published or deleting it removes its rows. Draft, pending and private events therefore have no occurrence rows. Each event's stale rows are deleted and its replacement rows inserted inside one transaction, so a failed insert preserves the previous set. Occurrence rows copy the assigned event type (the lowest term ID when several are assigned), coordinates from the venue with parish fallback, and the cancellation flag. An archdiocese-wide event stores a NULL parish and NULL coordinates. Cancelled events keep their dates with `is_cancelled = 1`; postponed events keep their dates with `is_cancelled = 0` and remain distinguishable by the event post's status flag. A separate source-polling adapter/job is not registered.
The retention job removes only opted-in raw copies, attachment files, expired tokens and old audit rows; it leaves the message row, candidate metadata and attachment metadata needed for review, retries and health checks. For processed-folder mail, it deletes only exact UIDs recorded from successful plugin moves with a valid `COPYUID` receipt, scoped to the source, mailbox identity, processed folder and current destination UIDVALIDITY. Pre-existing messages, moves without a mapping and other untracked messages are never selected. Ownership records persist across completed runs so eligible mail can be pruned when it ages into the retention window; stale ownership is discarded without mailbox deletion when identity or UIDVALIDITY changes. Cleanup requires UIDPLUS for UID-scoped expunge and fails closed without it. When a terminal message ages out, the job clears both `raw_path` and `body_text` in the same verified transition, but messages still awaiting review or retry keep both. Raw cleanup honours the per-message `retention_until` floor written at ingest from the configured day limit, so shorter later settings do not shorten existing rows.

xneelo cron jobs can run at most every 2 hours, and there is no WP-CLI, so jobs have several triggers ([ADR 0010](decisions/0010-scheduled-jobs-with-2-hour-cron-limit.md)):
- WP-Cron stays on, so site visits run due jobs.
- One 2-hourly xneelo cron job calls `https://<site>/wp-cron.php?doing_wp_cron` over HTTP as a backstop.
- An optional free external pinger (cron-job.org) calls it every 5–10 minutes for timely intake.
- **Parish Intake → Scheduled jobs** lists each registered job and its last run, last success, last error, and last run's item count. The per-job **Run now** action is a capability- and nonce-protected POST that uses the same lock and budgets while bypassing only the due check. Running `poll_mailboxes` manually polls active mailboxes; later queue-processing jobs will provide the parsing and event-work checks.

The intervals above are "due" times: a job runs on the first trigger after it is due, including after a trigger gap of up to 2 hours. The scheduled-jobs page reports run state; the separate health-dashboard warning after 2 h 15 min remains a later dashboard feature.

## Trust, confirmation and approval (summary)

See [ADR 0004](decisions/0004-trust-and-confirmation-model.md) (confirmation, safe links) and [ADR 0008](decisions/0008-approval-by-dean-or-archdiocese-reviewer.md) (approval).

- **Every new event** goes through two steps:
  1. The **submitter confirms** the emailed preview.
  2. It then appears **at the same time** in the queue of the parish's **deanery approvers** (the dean) and of the **archdiocese reviewers**. The first to Approve or Reject decides.
- The #59 admin queue keeps **Awaiting approval** as an all-items scoped view while assigning each non-final candidate exactly one primary category: failed/pending-publication, awaiting submitter, unknown sender, low confidence, or ordinary approval. The first view overlaps the last three by design; primary category counts are disjoint. Rejected decisions are visible separately for 30 days. Ambiguous matches and pending duplicates require manual resolution and cannot bulk-publish. Deanery approvers can use only their review-queue screen in wp-admin; the portal remains future work. Each queue row shows the overall confidence and how many fields scored below the field threshold, and the candidate detail screen shows a read-only Field / Score / Evidence / Notes table so a reviewer can see at a glance which values the parser read and which it invented.
- The #58 **audit log** screen (`Parish Intake → Audit log`, capability `adct_pi_view_reports`) makes the existing `adct_pi_audit_log` rows viewable and filterable. It is **read-only by construction**: the filter form is GET, there is no POST handler and no nonce, so the screen cannot change a row even if one were added. Every field it renders — including `details`, which carries text that came out of a parsed email body — is escaped, and the details JSON is rendered as one escaped string, never as markup. It reads through `AuditLogReader`, so Core stays free of WordPress calls and the screen is testable without a database.
- The log is **effectively append-only**. #58 deliberately adds no edit or delete action and no way to remove a row; rows leave only via the 24-month retention job. If a future issue asks for deletion, it should be treated as a change to the trust model (ADR 0004 rule 7, ADR 0008 rule 10) and raised, not quietly built.
- The screen's default window is **3 months**, with a bounded 1/3/6/12/24-month choice and 25 rows per page, and the repository refuses a window longer than the retention period. The host's 90-second PHP limit and the unbounded size of the table make an open-ended scan unsafe, and a window wider than retention could only return a misleading partial answer.
- `event_published`, the seven `contact_*` actions and `settings_updated` had **no write site** before #58, so the trail was incomplete: an event appearing on the public site, a contact being blocked, or the retention window being changed all left no record. `ContactAuditRecorder` and `SettingsAuditRecorder` close those gaps. `event_published` is written inside the publish transaction, so a rolled-back publication leaves no row claiming it happened.
- The **candidate detail** screen (`ReviewQueuePage`, reached with `?candidate=<id>` on the same review-queue screen) shows one candidate's whole story in one place: the source message's subject, sender and body, its attachment list, every stored field, its recurrence rule, and its audit trail. Approvers edit title, dates and times, parish, venue, description, type, featured and status flags, plus the recurrence controls, and then Save, Save and approve, or Reject.
- **#63 manual entry beside the poster.** The same screen previews the first stored browser-readable image on that email (`image/jpeg`, `image/png` or `image/webp`) inline, beside the edit form, through the shared client-side OCR control, so a scanned or photographed notice can be read while the details are corrected. The inline image is scaled down to fit the side column, which is usually too small for the dates on a photographed A4 sheet, so the sentence under the **Poster** heading also links the identical, already-authorised URL as **Open the poster at full size** (`target="_blank"`, `rel="noopener"`). Because `AttachmentImageEndpoint::send()` streams the original stored bytes, the full-resolution poster needs no second endpoint, no second authorisation and no re-encoding — there is deliberately no lightbox or JavaScript for it. Each still-stored image attachment also carries a **Create event from this poster** button, which posts to a separate `admin_post` action (`adct_pi_candidate_create_manual`, its own `manual_nonce`) that inserts one blank candidate row for that email's next free `block_index`. The blank row starts `awaiting_approval` with `match_kind = new`, empty `fields` and no approver of any kind, and is then typed into and decided through the **unchanged** save route above. There is no separate manual approval path, so the `approved_via` allow-list in `CandidatePublisher` still applies unchanged; the button is refused on an out-of-scope, unrecognised or already-decided candidate, and the posted attachment id is trusted only after it is confirmed to belong to that candidate's own message. The button is offered only for images, never for a PDF or a file that is no longer stored. A PDF therefore still gets no inline preview and no manual-entry button: it keeps its text layer (ADR 0015) and stays downloadable, so an unparseable PDF is still handled on the Manual parser screen rather than here.
- Editing is **scoped like deciding**. A dean only reaches a candidate in their own parish's queue, `?candidate=` and the POST are re-checked with the same scope query on every request, and a candidate that has already been decided renders read-only with no save form. Dates are entered and displayed day-first (`DD/MM/YYYY`, `Africa/Johannesburg`) and stored as ISO; a rolled-forward date such as `31/02/2026` is rejected rather than silently shifted. Only the 14 declared editable field keys can be written; the submitter's contact details are shown read-only because re-pointing an event to a different sender is a manual-review decision, not an approver correction.
- The detail screen's **downloads** are served by `admin_post` handlers, not inline links. Each file is looked up through the protected-storage reader (name allow-list, symlink rejection, 10 MB cap) and the candidate's own message is compared against the requested attachment, so one approver cannot walk the attachment table. A MIME type recorded from parish mail is untrusted header input, so it passes through an allow-list and anything else is served as `application/octet-stream`.
- E4.2's **emailed** approval links and the #61 admin screen are the same decision, reached two ways. Both go through `ReviewQueueRepository::decide()` and write the same audit rows; the emailed token path is unchanged by #61. #61 added no resend of a confirmation preview. **#177 adds the ambiguous-match resolution** that was left as a separate issue: a candidate whose `fields` JSON carries `match_review_required` or `matched_candidate_id` is not approvable, so the detail screen renders a **Resolve this match** panel above the editor with its own `admin_post` action (`adct_pi_candidate_resolve_match`, its own `resolve_match_nonce`) — separate from the edit form so pressing Enter in a title field cannot resolve anything. It offers the parishes in the reviewer's scope plus a deliberate **Leave unassigned** choice, and an optional venue that must belong to the chosen parish. The handler resolves the candidate's scope again on every POST (never from the form), refuses an already-decided candidate, and calls the **same** `ReviewQueueRepository::assignParish()` the queue's bulk manual resolution uses, so routing and clearing the block happen in one transaction and one audit row. The two `fields` keys are **removed, not falsified**: `MatchReviewPolicy` reads presence, so `false` or `0` would re-block the candidate at the next match. The decision is audited under its own verb `candidate_match_resolved` rather than reusing `candidate_parish_assigned`, because resolution removes a block and not only routes a row, and the trail has to show that somebody cleared it. `ReviewQueuePolicy::canDecide()` now accepts `duplicate` as well as `awaiting_approval`, because `duplicate` is the status the matcher itself produces for an ambiguous match, so "resolved ⇒ approvable" would otherwise be false for exactly the rows this control exists to unblock.  One consequence is that the panel asks a different question from "give me the fields", and so it must not die when `fields` will not parse. `ReviewQueuePolicy::requiresMatchResolution()` therefore reads the two flag **columns** first and answers `false` rather than throwing when `fields` is unreadable; `fields()` itself still throws, and `canBulkApprove()` still calls it, because an approver must never proceed on a row it cannot read. The screen then withholds the resolve control for such a row (a correct resolve *rewrites* `fields` and would destroy the event we just failed to parse) and shows an explicit notice, so a screen that quietly offers neither control is never mistaken for one where there was nothing to resolve. Deliberately **not** in scope: a new "genuinely unresolvable" status, which is a separate open question about lifecycle rather than resolution.
- The E4.2 job queues the submitter preview only. E4.3 activates Confirm, Deny and Confirm-all through nonce-checked POSTs; submitter Edit remains inactive. A GET never decides an event. Confirmation status remains separate from candidate lifecycle, and suppressed previews cannot be acted on.
- E4.5 queues grouped priority-2 notices for active assigned deanery approvers and active reviewers, or priority-3 daily digests. Their Approve / Reject links require a nonce-protected POST and a deliverable queue item. Edit permits limited corrections (title, date, time, description) without approving; parish/venue changes and ambiguous matches need manual review. Decisions are conditional and audited; a failed publication can be retried with the winning token. Reminders after N days remain separate work.
- **Self-approval:** if the submitter is an approver for that parish, their confirmation publishes directly.
- **Verified sender:** the linked parish and venue can be filled in automatically. Every new event still follows submitter confirmation and the required approval path above. The instant handling of verified changes and cancellations in ADR 0008 is still not connected: `InboundMailPolicy::canApplyInstantChange()` exists and is tested, but `CandidatePublisher` still refuses any `approved_via` outside `dean`/`reviewer`/`self`, so `contact_change` remains unavailable until the verified-contact workflow supplies that proof. #71 landed the revert half of that story; the instant-publish half is still outstanding.
- **One-click revert (#71):** a change notice carries a `revert_change` link, and `RevertChangeHandler` restores the `before_payload` the change recorded, rebuilds occurrences, bumps the listing generation, and appends a `revert` row so the trail reads forwards. **The token is scoped to a recipient who may stop being entitled to it**, so the handler re-resolves the recipient's live approver role through `ApprovalRecipients::roleFor()` at act time, inside the transaction, exactly as `ApprovalDecisionHandler::role()` and `ConfirmationDecisionHandler::isActiveApprover()` do. A GET that no longer resolves a role shows no button, and a POST that no longer does is refused with the token left `valid`, so a dean moved between deaneries loses only the parish they no longer cover.
- **Unknown sender:** approvers see an "unknown sender" warning. E1.3 records the actual From address as an unlinked pending contact and shows an unambiguous parish match only as a labelled suggestion; a directory manager must choose the parish and explicitly confirm it, or block the address. Confirmation verifies the address but does not approve or publish its event candidates.
- **Sender learning (E1.3):** signature, parser, body and uniquely associated verified-contact domain matches are suggestion-only, never trust evidence or an automatic parish link. Ambiguous matches remain unlinked. The directory-management screen is for directory managers; #50 must add deanery-scoped approval-page confirmation after checking the approver's active assignment, not reuse the manager action. Printed bulletin addresses can inform manual contact entry only after explicit administrator review; they are never auto-created from attachment text.
- **Secondary/monitored source:** a "we found this on X, do you want it published?" email goes to the parish's known contacts. Their "yes" counts as the confirmation, and approval follows.
- **No dean needed:** parishes without a deanery, or in a deanery with no active approver set up yet, go to archdiocese reviewers only. The dashboard shows which deaneries have no approver.
- **Routine repeats are silent:** an unchanged event that appears again (e.g. in every weekly bulletin) is matched to the existing event and not sent for confirmation or approval again ([parser findings](parser-samples.md)).
- Mailbox screening treats `Auto-Submitted`, autoreply headers and delivery-status reports as declared automation; list/precedence headers, null `Return-Path` and no-reply-style addresses are likely automation. Both classifications set the persisted no-confirmation flag, including for mailing lists. The Core `InboundMailPolicy::canSendConfirmation()` also rejects unsafe sender or reply-to addresses; mailbox polling does not send confirmations.
- SPF/DKIM/DMARC verdicts are stored as structured `auth_results`, never as rendered raw headers. An unknown or untrusted authserv-id is not a verified pass and cannot grant sender trust. A reported DMARC failure on a verified contact is shown as a review flag, and `InboundMailPolicy::canApplyInstantChange()` returns false for that message; connecting that policy to the approval route is still outstanding.
- To change an event, reply with the changes, or click *Edit* (magic link) and edit it in the portal.

## Parish self-service

Parish contacts are WordPress users with a custom `parish_contact` role, linked to one or more parishes. They log in with a **magic link** sent to their address. The auth cookie lifetime is extended (1 year, configurable with `ADCT_PI_AUTH_COOKIE_LIFETIME_DAYS` in `wp-config.php`) for `parish_contact` and `deanery_approver` only, via `Plugin::authCookieExpiration()`; every other role keeps the WordPress default. The link itself is minted for `ActionTokenPurpose::LOGIN` at a 30-minute lifetime. Parish contact self-service &mdash; listing, editing, cancelling and duplicating their own events &mdash; is still future work; #72 delivers only the magic-link sign-in and the dean approval queue it unlocks. See [ADR 0007](decisions/0007-auth-with-wordpress-users-and-magic-links.md).

## Public output

- `adct_event` custom post type with a REST-enabled `adct_event_type` taxonomy. Its seeded Social, Spiritual, Formation, Liturgy/Mass, Youth, Outreach, Fundraising, Meeting and Other terms are **provisional and admin-editable**.
- An **occurrence table** holds each dated instance (once-off and expanded recurring), so date-range queries and "near me" sorting are simple SQL. Rows exist only for published posts, store UTC instants plus the SAST local date, and are replaced transactionally; a missing parish is stored as SQL NULL rather than a synthetic parish ID.
- The public listing's block and shortcode share bounded date/page/type/parish/deanery selection with a read-only REST fragment used for optional JavaScript filtering. Type selection checks every assigned WordPress taxonomy relationship (not only the occurrence row's lowest term ID); parish/deanery selection uses occurrence and directory columns. Only unfiltered preset pages use short-lived generation-keyed transients; arbitrary combinations remain uncached.
- **Near me** (ADR 0020): each parish/venue already carries latitude/longitude, entered once in the directory, so no new table and no migration are needed. A visitor opts in by pressing **Use my location** (the browser geolocation prompt never fires on its own) or by typing a suburb; declining or an unsupported browser simply reveals the suburb box, which is an equal route. A `PlaceCoordinateLookup` port resolves a suburb name against those stored coordinates and never calls a geocoding service, so no visitor input leaves the site. The visitor's choice lives in the URL (`adct_lat`/`adct_lng`/`adct_radius_km`, or `adct_suburb`) and nowhere else: it is never stored, logged, or cached, and the listing transient is skipped while a distance sort is active so anonymous visitors cannot grow `wp_options`. Ranking is a haversine expression computed in SQL (MySQL 8 and MariaDB 10.11 portable), with a real radius `WHERE` filter chosen from a fixed set; occurrences with no coordinates are left out rather than shown as "far away".
- An **ICS feed** covers everything, with filtered variants (per parish, per type), so people can subscribe in Google/Apple/Outlook calendars. The public listing renders a **subscribe block** beneath its status line: each link offers the feed as an ordinary URL and as a `webcal:` variant for one-tap import. The link set is chosen by the pure `Core\Events\IcsFeedLinks` helper — an unfiltered or parish-filtered listing offers the whole matching feed, and a type-filtered listing offers one feed per selected type (capped at `MAX_LINKS = 10`) rather than silently widening to every event. `?adct_ics=1` is stripped from filter, sort and pagination links so subscribing never disturbs the listing state.
- A "featured" flag separates big once-off events from routine recurring ones on the listing.

## Security notes

- Admin screens use dedicated capabilities for settings, directory management, review, reports and deanery approval. The pure role/capability map lives in `Core\Auth\Capabilities`; a versioned, additive installer creates custom roles and adds missing capabilities without replacing other role capabilities.
- `parish_contact` and `deanery_approver` are read-only roles. They cannot use `wp-admin` or the admin bar, except for AJAX and `admin-post.php` requests; users who also have editorial `edit_posts` access are not blocked.
- Deanery approvals require an active assignment in `adct_pi_deanery_approvers` matching the parish's `deanery_id`. `adct_pi_review` holders can approve across deaneries, including parishes without a deanery.
- Admin actions use capabilities + nonces. Portal actions check parish ownership.
- Authentication-Results headers are sender-controlled unless the receiving MTA removes external copies and stamps its own result. The trusted authserv-id allowlist is empty by default; configure only an exact ID after confirming the MTA's header-stripping/rewriting behavior. A matching header alone is not proof of sender identity.
- Mailbox settings always verify the TLS peer and hostname in production. A TLS failure advises operators to use the server hostname listed on its certificate; unencrypted connections and disabled verification remain explicit test-only options (ADR 0013).
- Action links use 32 CSPRNG bytes encoded as unpadded base64url; only the SHA-256 hash, purpose, subject, normalized email, expiry and used-at state are stored. Defaults are 14 days for event actions and 30 minutes for login. The front-end endpoint renders a handler-provided preview on GET without mutation; only a nonce-protected POST can atomically consume a token and invoke a registered handler. The form POST omits the token from its URL; responses are no-store, no-referrer and noindex. Unexpired/unknown purposes have no built-in business handler in this issue.
- New-link requests are POST-only and use atomic fixed-UTC-hour HMAC buckets: at most 3 requests per email and 20 per source IP. The limiter stores no raw email/IP and prunes inactive buckets after 48 hours. Renewal delivery uses `MailerInterface` and priority 1; it never calls `wp_mail` directly.
- Email HTML is never rendered unsanitised; attachments are stored outside the web root or with deny rules, and only allowed MIME types are processed.
- AI prompts treat email content as untrusted data; AI output is schema-validated and never decides publishing.
- Secrets are registered by purpose (`ADCT_PI_AI_API_KEY`, `ADCT_PI_IMAP_PASSWORD`, `ADCT_PI_OCR_API_KEY`). A non-empty string constant in `wp-config.php` takes precedence over its stored option; the Core resolver receives constant and option readers as injected callbacks, and the WordPress adapter supplies those readers. Empty or non-string constants fall back to the option. Mailbox passwords use a stable mailbox-ID scope: `ADCT_PI_IMAP_PASSWORD_MAILBOX_<ID>` overrides the default `ADCT_PI_IMAP_PASSWORD`, which overrides that mailbox's non-autoloaded option. Register future global secrets as `ADCT_PI_<PURPOSE>` constants paired with `adct_parish_intake_<purpose>` options; secret reads must go through the resolver. Secret values are not included in settings output, parse results, or debug output. Admin screens that only need to know whether a key is already stored (to offer a remove control rather than a paste prompt) depend on `Core\Security\SecretLookupInterface` rather than the concrete WordPress adapter, so the "'is it set'" question stays a port and is testable without a live options table.
- Uninstall removes the plugin's custom roles and its custom capabilities from built-in roles. Tables and plugin data are retained until the owner makes a separate data-deletion decision.
