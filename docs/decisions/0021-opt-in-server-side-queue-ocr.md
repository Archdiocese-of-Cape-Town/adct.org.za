# ADR 0021: Opt-in server-side queue OCR for image posters

- Status: Proposed
- Date: 2026-10-05

## Context
About 1 in 4 posters reaching the archdiocese is image-only. The rule-based parser has no text to work with, so those notices produce only an `Image-only poster` candidate flagged for manual entry, and a person types the event in by hand.

[ADR 0018](0018-client-side-ocr-for-image-posters.md) solves the same problem in the browser: a reviewer clicks, tesseract.js runs on their own device, and nothing is stored or sent to the server. That path cannot reach the two places automation is actually needed:

- **Ingestion has no browser.** `InboundMessageProcessingJob` is a cron job with a ~60 s budget inside a 90 s PHP limit ([ADR 0010](0010-scheduled-jobs-with-2-hour-cron-limit.md)). Nobody is present to click, so an image-only poster can never become a candidate without a human opening the Manual parser screen.
- **A poster that arrives before its deadline.** A confirmation email is sent to the submitter on arrival. Without OCR in the job, the submitter receives "we could not read your poster" for a poster whose text was perfectly legible.

[ADR 0015](0015-pure-php-pdf-text-extraction.md) rejected server-side OCR partly because the host cannot run an OCR binary: xneelo shared hosting has no OCR engine, no `pdftotext` and no Ghostscript. That reasoning still holds for *local* OCR, and it is why this ADR does not introduce one. It does not hold for a remote HTTP API, which needs nothing on the host.

The real cost of a remote API is not the binary but the **egress**. A parish poster is personal data under POPIA, and the repository is public. Sending one to a third party is a data-egress decision that the project owner, not a code reviewer, has to make. [ADR 0005](0005-offline-first-parsing-with-pluggable-ai.md) already established the pattern for exactly this: AI is a port, an adapter, an off-by-default setting and an unconditional fallback to the offline path.

Issue #14 (E12) is the phase-2 epic for optional AI/OCR plug-ins. This ADR covers the single-provider first step; the plug-in registry is deliberately out of scope.

## Decision
- **Send poster images to one remote OCR provider, OCR.space, and only when an operator has explicitly opted in.** OCR is off by default and is enabled by an Administrator or Intake manager on **Parish Intake → Settings**, in its own **Poster image OCR** section. It is a separate decision from the AI fallback with its own option, its own key and its own daily spend limit, so turning AI on or off does not turn OCR on or off. OCR.space is the host chosen here because its `apikey`-optional free tier needs no purchase order and no paid dependency; a different provider is an adapter behind `OcrProviderInterface`, not a rewrite.
- **Say exactly what leaves the site, on the screen where the decision is made.** The egress is the image attachment and nothing else: the sender's name, email address, subject line, body text, Message-ID and every other header stay on the server. The API key travels in the `apikey` request header, never in the request body, so it cannot land in a proxy log that also holds the body. The settings section states the destination host, the size ceiling and the fallback in plain language rather than leaving them to be inferred from the code.
- **Never let an OCR outcome change whether an email is processed.** `OcrTextEnrichmentService` returns the message untouched on every non-happy path, and the enrichment step in `InboundMessageProcessingJob` is the same shape as the existing PDF enrichment. OCR can only *add* a marked text section before parsing; it can never remove, reorder or fail the rest of the pipeline. Each degradation is recorded on the attachment row and shown to the operator as a notice, so "nothing happened" is always distinguishable from "the provider is broken".
- **Run only in the queue, with a hard timeout well inside the PHP limit.** Extraction is per-image capped at 15 MiB and 20 s, per-message at 3 images and 30 s, on a shared stopwatch so the second and third images see less remaining budget than the first. No OCR call happens on an admin page load. At most 3 posters per message are sent, so one bulletin full of posters cannot become one HTTP storm.
- **Count every attempt against a daily cap, before the call.** `WordPressOcrCallGate` reserves a unit *before* the request, so a call whose response never arrives still costs one — a retry loop cannot make the bill unbounded. The cap defaults to 20 posters a day and is configurable per installation, independent of the AI fallback's own cap. A 429 backs the gate off for 10 minutes and a 5xx for 5 minutes, so a provider incident does not spend the day's budget.
- **Never store or echo the key.** The key is held in a `private readonly \Closure` in the provider, which keeps it out of `print_r`, `var_export`, `var_dump` and `__debugInfo()`. The settings screen renders an empty password field plus "a key is saved", never the value, and the save handler records the fact of a key rather than the key. `ADCT_PI_OCR_API_KEY` in `wp-config.php` takes precedence over a stored key, matching the existing AI-key convention.
- **Mark what was read from a photograph, so an OCR candidate is never mistaken for a typed one.** The issue asks for OCR-filled fields to be marked lower confidence, and the existing evidence machinery does this without inventing a new scoring policy. `Pipeline` notes which block the marked OCR section opens and `ConfidenceScoringStage` adds the `ocr` weakness flag to every field of the candidates parsed from that block onwards, charging the flag penalty on top of the origin the field already earned. This is deliberately a **flag, not a weaker origin**: a plainly printed date on a poster really was stated, so the only extra reason to doubt it is that the characters came out of a photograph, and recording that as a separate weakness preserves the fact of how it was read instead of flattening it to the same score as any other machine reading. The candidate also carries an operator note, so an approver sees why the values need checking. Because a flag is only charged when something sets it, no candidate parsed without OCR changes score — which is why this needs no separate threshold setting.
- **Keep the client-side path as the default for people who are present.** ADR 0018 is unchanged and un-superseded. Client-side OCR still costs nothing, discloses no parish content to anyone, and remains the better answer on a review screen. Server-side OCR earns its place in the queue, where no button exists. Neither path is removed.

## Consequences
- An image-only poster can now produce a dated, venue-bearing candidate with no human typing it in, and the submitter gets a preview of what we read instead of a failure notice. Without this the manual path is the only route.
- **This is the plugin's first default-off flow that sends parish content to a third party.** The opt-in is per installation and reversible in one click: unticking the box means no image bytes leave the site again, and the daily counter and back-off option are inert. The project owner should read this record as the thing to reverse if that trade stops being right — reverting is unticking one checkbox, not a code change.
- The `ocr` penalty is calibrated so a poster-read `explicit` value falls below both the per-field threshold (0.60) and the review threshold (0.55), matching the score of an `ai`-read value, while staying well above zero so an imperfect poster still yields a usable candidate rather than a blank one. The consequence is that OCR-read values are routinely flagged uncertain in the submitter's preview email and held for a human; that is the intended behaviour, not a defect, and it is what keeps a photograph of a date from being published on OCR's say-so alone.
- A poster readable only as low-quality photography still yields poor text. This is why the enriched text is fed to the same deterministic parser rather than trusted: the candidate scores as evidence, and the existing approval step (every new event needs dean or archdiocese approval, [ADR 0008](0008-approval-by-dean-or-archdiocese-reviewer.md)) remains the gate. OCR output is never published directly.
- The provider is a single point of failure for this one feature and nothing else. It is behind `OcrProviderInterface`, whose methods return an outcome object and are contractually forbidden to throw, so a provider outage is a notice rather than a failed message.
- **Reversing the egress without losing the intake path is not free.** If the owner decides no parish poster may leave the site, the settings screen makes that a one-click change, but the automatic poster-to-candidate capability goes with it and image-only posters fall back to ADR 0018's browser path plus manual entry. That trade, not the code, is what the opt-in exists to make reversible.
- There is no schema change. Attachment reuse status, method and stored text use columns that already exist for PDF extraction, so no migration and no db-version bump are needed. This is only true while the provider is OCR.space; a provider needing a new per-attempt record would require a versioned migration ([ADR 0016](0016-pre-release-schema-changes.md)).
- The vision-model provider named in issue #75's title is **not** built. Adding it, or making either provider pluggable by third parties, is issue #14. This ADR deliberately ships one adapter so the shape can be reviewed before it is generalised.
